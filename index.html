Multi-cycle RV32I CPU와 APB SoC

github.com/jeongmin-0113/proj_rv32i_multi_cycle_cpu

RV32I 정수 명령어를 지원하는 CPU를 single-cycle로 만든 뒤 multi-cycle로 재설계하고, APB 버스로 RAM과 GPIO를 붙였습니다. C로 쓴 1~10 누적합 프로그램을 RISC-V로 컴파일해 ROM에 올리고, 결과값 55가 RAM에 저장되는 것까지 waveform으로 확인했습니다.

내가 한 일

  • Control unit을 FETCH, DECODE, EXECUTE, MEMORY, WB 5-state FSM으로 설계. R/I/B/U/J는 3 cycle, Store는 4 cycle, Load는 5 cycle에 APB wait를 더한 만큼 걸리도록 명령어 type별로 필요한 state만 거치게 함
  • Datapath는 mux 세 개(ALU operand, write-back 5:1, PC 3:1)로 모든 명령어 type을 처리하도록 구성
  • Load/Store에서 CPU는 transfer, bus_addr, bus_wdata를 APB requester에 넘기고 ready를 기다리게 해서, CPU 쪽에서는 peripheral을 memory-mapped 주소로만 보도록 경계를 나눔
  • C, assembly, HEX를 거쳐 $readmemh로 ROM에 올리는 흐름을 만들고 JAL/ret, stack frame, APB read로 ra를 복원하는 과정을 waveform으로 검증

고민과 개선

−현상GPIO 제어 SW로 ROM을 바꾸자 10ns 제약에서 negative slack 발생
?원인명령어가 바뀌는 동안 다음 단계 logic이 같은 cycle 안에 묶여 path가 길어짐
+개선Instruction Register를 추가하고 state별 enable 신호를 다시 짜서 WNS +0.475ns 확보
−현상PC update path가 critical path 후보로 지목됨
?원인Branch, JAL, JALR을 위한 mux 단이 많아 PC path가 길어짐
+개선JALR의 rs1+imm이 ALU add와 같다는 점을 이용해 ALU 결과를 PC 입력으로 재사용하고 mux 한 단 제거

Timing report에서 single-cycle과 multi-cycle 모두 critical path가 datapath가 아니라 PC next 계산 path라는 점을 확인했습니다. 예상과 달라서 오히려 기억에 남은 결과입니다.

팀 범위는 multi-cycle CPU, APB, RAM·GPIO slave, R·I type UVM 검증까지입니다. Pipeline과 APB-UART 연동은 포함되지 않았습니다.

동기식 FIFO 설계와 UVM 검증 환경

github.com/jeongmin-0113/ai_semiconductor_bootcamp_archive/Verilog_HDL/FIFO_UVM

8bit × 16 slot 동기식 FIFO를 직접 설계하고 UVM 검증 환경을 처음부터 구성했습니다. 목표였던 coverage 80%를 넘어 100%를 달성했고, 모든 test에서 fail 0건을 확인했습니다.

내가 한 일

  • FIFO를 register file과 control unit으로 나누고, 데이터를 shift하는 대신 wptr/rptr pointer를 옮기는 구조로 설계. Full일 때 push, empty일 때 pop, push/pop 동시 입력 상황을 state별로 정의
  • Sequence, driver, monitor, scoreboard, coverage로 UVM 환경 구성. Scoreboard에 reference buffer를 두고 push/pop마다 pass, fail, skip을 판정
  • Pop 다음 posedge에 출력이 바뀌는 combinational output 특성에 맞춰 monitor는 input #1step, driver는 output #1로 clocking block timing을 설계
  • i_data/o_data의 256개 bin은 FIFO 동작 검증과 관계가 없어 제외하고, push×pop, push×full, pop×empty cross로 corner case를 coverage에 직접 포함

고민과 개선

−현상full coverpoint가 50%에 머묾
?원인Random sequence만으로는 FIFO가 full 상태에 도달하지 못함
+개선연속 push만 보내는 full_seq를 추가해 full 상태와 full일 때 push하는 corner case를 검증
−현상Stimulus 생성이 끝났는데 monitor만 계속 돌며 simulation이 끝나지 않음
?원인마지막 구간에서 objection을 drop하지 않음
+개선Test의 run_phase에 drop_objection을 추가하고 마지막 sequence 시점(220.5ns)을 waveform으로 확인

Coverage 100%라는 숫자를 끝으로 보지 않았습니다. 한 입력에 push와 pop이 함께 오면 두 번 판정되어 count가 맞지 않는 scoreboard의 한계도 결과 보고에 그대로 적었습니다.

DHT11 센서 controller와 UART 통합

github.com/jeongmin-0113/ai_semiconductor_bootcamp_archive/Verilog_HDL/DHT11_controller

Single-wire로 송수신을 번갈아 하는 DHT11 온습도 센서의 controller를 RTL로 설계하고, UART와 FIFO를 거쳐 PC 명령으로 센서 값을 주고받는 시스템에 통합했습니다.

내가 한 일

  • Datasheet의 start, response, 40bit data, checksum timing을 FSM으로 옮기고 half-duplex inout port를 처리
  • Datasheet timing spec에서 expected value를 역산해 self-checking testbench를 만들고, random 100회와 checksum 검사로 판정을 자동화
  • UART로 들어온 문자 command를 해석하는 ASCII decoder와, 센서 값을 문자로 바꿔 보내는 encoder를 설계
  • 보드에서는 ILA로 내부 state와 trigger 신호를 캡처해 simulation과 실제 timing을 비교

고민과 개선

−현상정상 동작이어야 할 구간에서 testbench가 fail 판정
?원인Waveform으로 어긋나는 구간을 좁혀 보니 비교 연산의 signed type 때문에 오판정
+개선Data type을 바로잡고 같은 scenario를 다시 돌려 판정 logic 검증

DUT가 아니라 testbench 쪽 bug였습니다. 검증 환경도 검증 대상이라는 것을 이 프로젝트에서 처음 체감했습니다.

STM32 아날로그·디지털 시계 firmware

github.com/jeongmin-0113/proj_analog_clock_stopwatch

Step motor로 시계 바늘을 움직이는 아날로그 시계와, FND와 I2C LCD로 보여 주는 디지털 시계·stopwatch를 하나의 firmware로 만들었습니다. 시간은 DS3231 RTC와 동기화하고, 이후 DHT11, SR04, buzzer까지 통합했습니다.

내가 한 일

  • Driver, service, app 계층을 나눠 button, LED, FND, LCD, DS3231, step motor driver를 직접 작성. 상위 계층은 set 함수로 데이터만 넘기고 hardware 세부는 driver에 캡슐화
  • Timer 3개로 역할 분리: TIM3 1ms interrupt로 FND 4-digit dynamic scan, TIM4 10ms로 시간 계산, TIM9 3ms마다 바늘을 target step까지 한 step씩 이동(1회전 4096 step)
  • DS3231은 BCD encode/decode와 repeated start read로 1초마다 시간, 1시간마다 날짜를 동기화
  • LCD는 이전 값과 비교해 바뀐 경우에만 갱신해서 I2C transaction 수를 줄임
  • Button 입력을 circular queue에 event로 쌓아 main loop에서 하나씩 처리하고, PWM 주파수를 바꿔 event별 buzzer음 출력

고민과 개선

−현상Mode 전환이나 시간을 크게 옮길 때 바늘 제어 코드가 따로 필요해 보임
?원인바늘 위치를 시간 값에 직접 묶으면 상황마다 분기가 생김
+개선Current step과 target step만 두고 ISR이 차이를 좁히게 해서 평소 동작과 mode 전환을 같은 logic으로 처리
−현상센서 통합 뒤 DHT11 값이 초기값 0에서 갱신되지 않음
?원인1ms FND interrupt가 μs 단위 DHT11 수신을 끊어 checksum 실패
+개선FND ISR을 끄면 정상 측정됨을 확인해 원인을 확정. 수신 구간 보호 방식은 개선 중

FPGA stopwatch와 시계

github.com/jeongmin-0113/fpga_proj_watch_stopwatch

처음 진행한 팀 프로젝트입니다. Stopwatch와 시간 조정이 되는 시계를 하나의 top에 넣고 switch로 전환하게 만들었습니다. 이후 센서 입력을 붙인 확장 버전도 만들었습니다.

내가 한 일

  • Modulo 값(100, 60, 60, 24)만 바꿔 재사용하는 parameterized counter로 carry chain 구성
  • Watch datapath에 up/down 조정 counter와, 조정할 digit을 선택하는 demux 설계
  • Button을 switch로 gating해 두 mode가 button을 공유하도록 top 통합
  • Stopwatch 기록을 저장하고 불러오는 save/load state와 saved flag feedback 추가

고민과 개선

−현상sec, min, hour가 매 clock마다 증가
?원인o_tick을 0으로 내리는 분기가 if(i_tick) 안에만 있었음
+개선else 분기로 옮겨 다음 posedge에 바로 deassert
−현상Simulation에서는 되던 load가 보드에서는 run처럼 동작
?원인LOAD state encoding이 RUN과 같은 3'b001
+개선LOAD에 고유 encoding 부여. 단위 testbench가 control unit을 거치지 않아 놓쳤다는 점을 확인

하위 module 단독 test만으로는 부족하고, control unit을 포함한 top-level scenario로 검증해야 보드 동작과 맞는다는 것을 배웠습니다. 이후 검증을 깊게 공부하게 된 출발점입니다.
